# イベント管理機能

この文書は「`items`統合・`notes`追加時の実装」を反映しています。この文書と現行の型定義に相違があった場合、現行の型定義を優先してください。

## 概要

自由ヶ丘執行委員会の活動のメインであるイベント開催に関する情報を総合的に管理する機能。

**設計思想: 企画書中心アプローチ**

- イベント管理機能に登録した情報を企画書としてエクスポート（Markdown形式）
- 完全自動化ではなく「コピペ補助」レベルを目指す
- 手動で追記すれば提出可能な企画書が生成できる

---

## 背景・目的

### なぜイベント管理機能が必要か

- 過去のバージョンではタスク管理機能とイベント管理機能が独立していた
- 実際の運用では「イベントごと」にタスクを割り振っている
- 独立したタスク管理機能より、イベント管理機能内にタスク管理を内包する方が実態に即している

### 従来の運用との違い

**従来:**

- Google Document で手動で表を作成
- イベントごとに情報が散在
- 企画書作成時に情報を集約する手間

**イベント管理機能導入後:**

- 一元管理された情報
- 企画書を自動生成（Markdown）
- 情報の見返しやすさ向上

---

## 設計思想 / 方向性

### 基本方針

- イベント管理機能は独立した機能として実装
- 他機能（議事録機能など）とは疎結合
- イベント内で情報が完結
- シンプルな権限管理（全員編集可能）

### 柔軟な型定義

- 企画書の実態を十分に表現できるように
- 過度に複雑化せず、必要十分な柔軟性を持つ
- オプショナルフィールドの設計が実運用に即している
    - 「イベント名だけで作成可能」という設計が、段階的な情報追加を自然にサポート
    - UI側で value || "-" のような処理が必要だが、これは妥当なトレードオフ
- Record型の柔軟性
    - roles, timeTable, referenceUrls がすべて Record<string, string>
    - 企画ごとに異なる項目に対応できる
    - ただしキー重複のリスクは運用でカバー

## データ構造

### 基本設計

**イベントメタデータ（親）と各タブ情報（子）のリレーション**

- イベント基本情報（Event）
    - イベント内容（EventContent）: 1対多
    - タスク（EventTask）: 1対多
    - 備品（EventEquipment）: 1対多 [Items]
    - 景品（EventPrize）: 1対多 [Items]
    - ノート（EventNote）: 1対多 [Notes]

### 型定義の特徴

**日付の扱い:**

- すべての日付フィールドは `string` 型（ISO 8601形式）または `string` へシリアライズ可能な状態で管理
- 理由: Server Component → Client Component のシリアライズに対応

**リスト型フィールド:**

- 宣伝方法（promotionMethods）: `string[]`
- 企画内の準備物（equipment）: `string[]`
- 参考URL（referenceUrls）: `string[]`

**JSON型フィールド:**

- 当日運営役割（roles）: `Record<string, string>`
- 例: `{ "司会": "山田", "副司会": "佐藤" }`

## 画面構成

### URL構造

物品管理（備品・景品）が `items` 以下のパスに統合され、ノート機能が追加されました。

```
/events                    # イベント一覧
/events/[id]/basic         # 基本情報タブ
/events/[id]/content       # イベント内容タブ
/events/[id]/tasks         # タスクタブ
/events/[id]/items         # 物品管理タブ（リダイレクト用）
/events/[id]/items/equipment # 物品管理タブ > 備品ビュー
/events/[id]/items/prizes    # 物品管理タブ > 景品ビュー
/events/[id]/notes         # ノートタブ（一覧）
/events/[id]/notes/[noteId] # ノート詳細
```

### ページ構成

### 1. イベント一覧（`/events`）

**表示内容:**

- イベント名
- カテゴリ（大イベント/小イベント）
- ステータス（企画中/開催中/開催済み/アーカイブ）
- 開催日時
- 開催場所
- 概要（2行まで）

**レイアウト:**

- カード型グリッド表示
- PC: 3列、タブレット: 2列、スマホ: 1列

### 2. イベント詳細（共通ヘッダー + タブ）

**共通ヘッダー（全タブで表示）:**

- イベント名
- カテゴリバッジ
- ステータスバッジ
- 概要（2行まで）
- 開催日時
- 開催場所
- 参加想定人数

**タブナビゲーション:**

- App Router のページで管理（状態管理不要）
- URLで状態を保持（共有可能）
- アクティブタブをハイライト

## タブ詳細

### タブ1: 基本情報

**表示項目:**

- 開催目的（複数行テキスト）
- 基本情報（2列グリッド）
    - イベント名
    - カテゴリ
    - 開催日
    - 開始時間 / 終了時間
    - 準備開始時間（オプション）
    - 開催場所
    - 参加想定人数
    - イベント予算
    - イベント責任者（オプション）
- ターゲット層（複数行テキスト）
- 宣伝方法（リスト表示）
- 当日運営役割（2列グリッド）
- 参考URL（オプション）
- メモ（オプション/Markdown）

### タブ2: イベント内容

**表示形式:**

- アコーディオン形式（展開/折りたたみ）
- 企画ごとにカード表示

**各企画の項目:**

- 企画名
- 概要
- ルール説明
- 企画の流れ
- 準備物（リスト）
- 参考URL（リスト）
- メイン担当者（オプション）

**企画と備品の関係:**

- 企画内の準備物と全体の備品タブは**独立**（参照整合性なし）

### タブ3: タスク

**表示形式:**

- カテゴリごとにグループ化
- カテゴリ内で順序管理（order フィールド）

**カテゴリ:**

- 企画立案段階 / イベント内容・準備 / 宣伝 / リハーサル / 本番（最終確認） / 任意カテゴリ

**各タスクの項目:**

- タスク名
- 期限（オプション）
- 担当者
- 完了/未完了（チェックボックス）
- メモ（オプション）

### タブ4: 物品管理 (Items)

**概要:**

備品と景品を統合したタブ。内部で「備品」「景品」のサブナビゲーションを持つ。

### サブビュー1: 備品 (Equipment)

**表示形式:** テーブル表示

**項目:**

- No.
- 品名（数量込み、例: "ペン 5本"）
- 用途
- 調達状況（既存/要購入/購入済）
- 価格（購入する場合）
- 備考（オプション）
- 参考リンク

### サブビュー2: 景品 (Prizes)

**表示形式:** テーブル表示

**項目:**

- No.
- 品名
- カテゴリ（大景品/中景品/小景品）
- 想定価格
- 実購入価格
- 購入先候補
- 一言紹介
- 提案者
- 参考リンク

### タブ5: ノート (Notes)

**概要:**

イベントに関する雑多なメモ、議事録の要約、アイデア出し、振り返りなどをMarkdown形式で記録する機能。

**一覧画面:**

- カード形式でノートを表示
- タイトル、カテゴリタグ、作成者、更新日時を表示
- カテゴリに応じたアクセントカラー表示（blue, green, yellow, pink, purple, gray）

**詳細画面:**

- Markdownビューアーによるリッチテキスト表示
- 編集機能（将来実装予定）

**各ノートの項目:**

- タイトル
- 本文（Markdown）
- カテゴリ（自由入力タグ: "宣伝", "振り返り"など）
- カラー（視認性向上用）
- 作成者 / 最終編集者

## 技術実装

### アーキテクチャ

**Server/Client 分離:**


```typescript
// page.tsx (Server Component)
export default async function EventPage({ params }: { params: Promise<{ id: string }> }) {
    const { id } = await params;
    const event = getEventById(id); // データ取得
    if (!event) notFound();
    return <ClientComponent event={event} />; // Client Componentへデータを渡す
}`
```

## 設計判断の記録

### なぜタブをページで管理するのか

**検討した選択肢:**
1. React の状態管理（useState）
2. App Router のページ

**選択: App Router のページ**

**理由:**
- URL で状態を保持（共有可能）
- ブラウザの戻る/進むが自然に動作
- 状態管理のボイラープレートが不要
- タブごとに異なるデータ取得ロジックを書きやすい

### なぜ企画の準備物と備品タブを独立させるのか

**完全に独立:**
- 企画内の準備物 → 気軽にメモ書き
- 備品タブ → 抜け漏れチェック、購入管理

**リレーションを持たせない理由:**
- 運用上、企画段階と最終確認段階で管理粒度が異なる
- 自動同期は混乱を招く可能性
- シンプルさを優先

### なぜ日付を string 型にするのか

**理由:**
1. Server Component → Client Component のシリアライズ
   - Date オブジェクトは JSON 化時に ISO 文字列になる
   - 型定義と実際の動作を一致させる
2. Prisma（データベース）との親和性
   - Prisma は DateTime を ISO 文字列で返す
3. フロントエンドでの柔軟性
   - 必要に応じて `new Date()` で変換

### 備品と景品を `items` にまとめた理由

**理由:**

- どちらも「調達するもの」「金銭が関わるもの」という性質が共通している。
- タブの数が増えすぎるとスマホでの操作性が低下するため、類似機能はグループ化した方がUIがスッキリする。

### ノート機能を追加した理由

**理由:**

- 「タスク」や「基本情報」には収まらない、フロー情報（アイデア出しの過程や、当日の細かい反省点など）を記録する場所が必要だった。
- 用途例: 振り返り、SNS発信内容など
- 議事録（Google Docs）へのリンクだけでなく、アプリ内で完結して読めるテキスト情報があると振り返りが容易になるため。
